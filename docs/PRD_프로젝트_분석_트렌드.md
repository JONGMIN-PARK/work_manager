# PRD: 프로젝트 분석/트렌드 뷰 (운영자 모드 Phase 2)

> **Version**: 1.0
> **Date**: 2026-06-10
> **Status**: Draft
> **연관**: 운영자 모드 Phase 1(v13.112, 🛡️ 운영자 탭 — 전체 가시성·포커스 셋·접근관리) 후속. Phase 3는 AI 인사이트.

---

## 1. 개요

운영자(admin + 부여된 사용자)가 **프로젝트별/전사 진척 상황과 트렌드**를 한 화면에서 분석할 수 있는 뷰를 🛡️ 운영자 탭에 추가한다. 산재한 데이터(진척률 히스토리·마일스톤·투입시간·이슈·일정)를 집계·시각화하여, "지금 잘 되고 있는가 / 어디가 위험한가"를 빠르게 파악하게 한다.

### 1.1 배경

- Phase 1로 운영자는 **전체 프로젝트를 보고 선택 숨김(포커스 셋)** 할 수 있게 됨. 그러나 "보기"만 가능하고 **분석·추세 파악 도구가 없음**.
- 진척 데이터는 이미 풍부하게 쌓이고 있음 — `progress_history`(일별 진척률·투입시간 스냅샷), `milestones`(보고 진척률·목표·보고 투입), `milestone_progress_logs`(작업 노트 이력), `work_records`(업무일지 투입), `issues`.
- 그러나 이들을 **한 곳에서 집계·비교·추세**로 보여주는 화면이 없어, 운영자가 여러 탭을 오가며 수동 판단해야 함.
- A/S 영역엔 이미 트렌드·통계(`as-stats.js`, Chart.js)와 Claude 인사이트(`as-ai.js`) 패턴이 있어 **재사용 가능**.

### 1.2 목표

| 목표 | 측정 기준 |
|------|-----------|
| 운영자가 프로젝트 상태/위험을 30초 내 파악 | 진입~핵심 지표 인지까지 클릭 수 ≤ 2 |
| 지연·공수초과·정체 프로젝트 자동 식별 | 위험 배지가 실제 위험 프로젝트를 100% 표기 |
| 기존 데이터 재사용(신규 수집 없음) | 신규 테이블 0, 기존 엔드포인트/집계 함수 재사용 |
| 포커스 셋과 일관 | 분석 대상 = 운영자가 보기로 선택한 프로젝트 집합 |

### 1.3 비목표 (Out of Scope)

- AI 자연어 인사이트 → **Phase 3**에서 별도.
- 데이터 수집 방식 변경(업무일지 입력 흐름 등) → 변경 없음.
- 외부 BI 도구 연동/내보내기(CSV/PDF) → 후속 검토(P3).

## 2. 사용자 & 접근 권한

- **대상**: 운영자 = `admin` 또는 관리자가 부여한 사용자(`isOperator()`). 일반 사용자에겐 탭/엔드포인트 비노출(서버 403). Phase 1의 `requireOperator`/`isOperator` 재사용.
- **분석 대상 데이터 범위**: 운영자 **포커스 셋**(`pmGetProjects()` 결과 = 전체보기 − 숨김). 숨긴 프로젝트는 분석에서도 제외.

## 4. 기능 요구사항

### 4.1 화면 구성 (운영자 탭 내 서브 섹션)

운영자 탭(`mOperator`/`operatorWrap`)에 상단 보조 탭(또는 섹션 토글) 추가:
`[가시성 관리(기존)] [📊 분석/트렌드] [👥 접근관리(기존)]`

분석/트렌드 섹션 레이아웃:

```
┌ 전사 개요 ─────────────────────────────────────┐
│ KPI 카드: 프로젝트 N · 평균진척 % · 총투입 h ·    │
│           지연 n · 공수초과 n · 정체 n            │
│ 상태 분포(도넛)   단계 분포(가로 바)             │
├ 위험 프로젝트 ─────────────────────────────────┤
│ 리스트: [프로젝트][상태][진척%][지연/초과 배지]   │
│        클릭 → 아래 상세 분석으로 포커스          │
├ 프로젝트 상세 분석 (선택된 1개) ───────────────┤
│ 진척률 추세선 + 투입시간(2축)   ← progress_history│
│ 담당자별 투입 vs 목표(바)       ← calcHoursByMs  │
│ 마일스톤별 진척/일정/투입(표)                    │
│ 최근 작업 노트 타임라인          ← msLogsGet      │
└────────────────────────────────────────────────┘
```

### 4.2 전사 KPI (FR-1)

포커스 셋 프로젝트 대상 집계:

| 지표 | 계산 | 데이터 |
|------|------|--------|
| 프로젝트 수 | count | projects |
| 평균 진척률 | mean(progress) | projects.progress |
| 총 투입 | Σ(업무일지 멤버한정 + 보고 투입) | calcHoursByMilestone / reported_hours |
| 목표 대비 | 총투입 / Σ목표 | assignee_targets |
| 예상 대비 | 총투입 / Σ estimated_hours | projects.estimated_hours |
| 지연 | autoProjectStatus==='delayed' 또는 today>end_date & progress<100 | projects |
| 공수초과 | 총투입 > 목표(또는 예상) | 집계 |
| 정체 | 최근 N일 progress_history 변화 ≈ 0 | progress_history |

### 4.3 트렌드/추세 (FR-2)

- **진척률 추세선**: `progress_history`(project_id, date, progress, actual_hours)를 시계열로. Chart.js 2축(진척% / 투입h). 이미 `renderProgressHistoryChart`(project-detail.js) 존재 → **재사용/확장**.
- **번업(Burn-up)**: 누적 투입 vs 예상/목표 라인. 계획선(예상=100% 기준 등속) 대비 실제.
- **전사 기간 추세(P2)**: 주/월 버킷으로 평균 진척·총 투입 추세(스택/라인).
- **속도/벨로시티(P2)**: 최근 7/14일 진척률 증가량(%/일)로 완료 예상일(ETA) 추정.

### 4.4 투입/편중 분석 (FR-3)

- 담당자별 투입(업무일지 멤버한정 + 보고) vs 목표 → `calcHoursByMilestone` 결과(`people`/`outPeople`/`reportedHours`) 재사용. 초과/잔여 표시.
- 마일스톤별: 진척% · 투입/목표 · 일정 D+/잔여 · 미태깅 건수.
- **할당 외 기록**(비등록자, `outPeople`)을 별도 표기(집계 제외 유지).

### 4.5 위험 자동 식별 (FR-4)

프로젝트별 위험 플래그(기존 투입실적 배지 로직 재사용):
- 🔴 공수초과: 총투입 > 목표(또는 예상)
- 🟠 일정지연: today > end_date & progress < 100 (D+ 일수)
- ⚠️ 진척 정체: 최근 N일 progress 변화 < 임계치(예: 14일간 +0%)
- ⚠️ 효율주의: (투입/목표) − (progress/100) ≥ 0.3

위험 프로젝트는 전사 개요 상단에 우선 노출 + 상세 분석으로 바로 드릴다운.

### 4.6 작업 노트 타임라인 (FR-5)

선택 프로젝트의 마일스톤 `milestone_progress_logs`를 시간순 통합 → 진척%·보고투입·작성자·노트. 기존 `msLogsGet` 재사용.

## 7. 기술 설계 개요

### 7.1 클라이언트 (신규 `operator-analytics.js` 또는 operator-mode.js 확장)

- `renderOperatorAnalytics()` — 전사 개요 + 위험 리스트 렌더.
- `renderProjectAnalytics(projectId)` — 상세(추세선·투입·마일스톤·노트).
- 집계는 가급적 **클라에서 기존 함수 재사용**(calcHoursByMilestone, getProgressHistory, msGetAll). 다건 프로젝트 집계는 캐시(`_pdCached`)·동시요청 병합.
- 진척률 추세선은 `renderProgressHistoryChart` 일반화하여 재사용.

### 7.2 서버 (선택 — 성능 필요 시)

대부분 기존 엔드포인트로 충분. 전사 집계가 무거우면(N 프로젝트 × 다건 fetch) 보조 엔드포인트 추가 검토:
- `GET /api/projects/analytics/summary` (운영자 전용) — 포커스/전체 프로젝트의 진척·투입·지연·정체를 서버에서 1회 집계(progress_history·milestones·work_records 조인). `requireOperator`.
- (P2) `GET /api/projects/:id/analytics` — 단일 프로젝트 상세 집계.

> 1차는 **클라 집계 우선**(엔드포인트 0), 성능 이슈 시 서버 집계로 이관.

### 7.3 캐시/성능

- 클라: 분석 진입 시 `progressHistory`·`msGetAll`·archive를 캐시 활용. 포커스 변경/탭 재진입 시 `_modeRendered` 무효화.
- 전사 집계 5분 캐시(이미 autoUpdateProgress throttle과 정합).

## 11. 미해결/결정 필요 사항

1. **분석 대상 범위**: 포커스 셋 고정 vs 분석 탭 자체 필터(상태/기간/담당자) 추가 여부.
2. **정체(stale) 임계치**: 며칠간 진척 변화 0%를 "정체"로 볼지(기본 제안 14일).
3. **위험 기준 가중**: 공수초과/지연/정체 중 우선순위·복합 점수화 여부.
4. **집계 위치**: 클라 집계 1차 → 서버 집계 전환 시점(프로젝트 수 임계).
5. **완료 프로젝트 포함 여부**: 분석에서 완료(done) 포함/제외 토글.
6. **권한 세분화**: 운영자 중 분석만 보는 역할 vs 가시성 관리까지 — 현재는 동일 운영자 권한.
