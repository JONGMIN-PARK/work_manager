## 1. v13.29 — 업무일지 가져오기 충돌 미리보기 + 컬럼 round-trip

### 사용자 보고
> "상세 → 📤 엑셀저장"으로 저장한 파일을 다시 불러왔을 때, 다른 일반 업무일지 엑셀과 컬럼이 일치하지 않아 처리가 꼬임. DB 테이블과 비교해서 (날짜, 이름, 수주번호) 키로 동일한 것이면 갱신할지 물어보고 업데이트하면 어떨까?

### 원인 분석
1. **export ↔ import 컬럼 불일치**: export는 `이름·날짜·수주번호·수주명·거래처·시간·업무분장·약자·업무내용` 9컬럼. import의 `COL_PATTERNS`에는 `수주명(ocmt)`, `거래처(oclient)`가 없어서 무시됨 → 사용자가 편집모드로 고친 ocmt/oclient가 round-trip 시 사라짐.
2. **헤더 패턴 충돌**: "수주명"이 `orderNo` 패턴 `/수주번호|수주|.../`에도 매칭되어 셀이 잘못 잡히는 잠재 버그.
3. **식별 키가 너무 엄격**: 기존 `wrIdKey = date+name+orderNo+hours+content` → 시간만 바뀐 동일 레코드를 별개로 추가.

### 변경 내역
**`업무일지_분석기.html`**
- `COL_PATTERNS`에 `ocmt`(수주명·프로젝트명·사업명·건명), `oclient`(거래처·고객사·업체·발주처) 추가.
- `COL_ALL` 우선순위 재배열: 구체적 패턴(`ocmt`/`oclient`)을 일반 패턴(`orderNo`) 앞에 배치.
- `pDetectColumns`에 `claimed[idx]` 추적 추가 — 한 셀이 더 구체적인 키에 매칭되면 다른 키가 다시 잡지 못하게.
- `pMapRow`에 `ocmt`/`oclient` 추출 추가 (cells 값이 비어있지 않을 때만 — ORDER_MAP 기본값을 가리지 않도록).
- 누락 컬럼 안내(`labels`)는 `ocmt`/`oclient` 제외 — 선택 컬럼이므로 누락되어도 안내 불필요.
- **`wrLooseKey`** = `date+name+orderNo` 신설.
- **`wrAnalyzeImport(existing, newRecs)`** 신설: existing 자체 dedup 후 `identical`(완전일치) / `conflicts`(시간/내용 차이) / `newRows`(후보 없음) 분류. `consumedExisting` Set으로 같은 existing이 두 번 매칭되는 것 방지.
- **`wrApplyDecisions(newRecs, analysis, decisions)`** 신설: 행별 결정(`update`/`skip`/`add`) 적용. `claimedForUpdate` Set으로 같은 existing 후보가 여러 newRec의 update 대상이 되는 것 방지. `mode='replace_keep_matched'` 옵션 — 매칭 안 된 기존 삭제.
- **`showImportPreviewModal(analysis, opts)`** 신설: 신규/자동갱신/충돌 카운트 + 충돌 행 테이블(날짜·이름·수주번호·기존vs새 시간·내용 diff). 행마다 select(기존 유지/새 값으로 갱신/별개 추가), 일괄 버튼 3종, "매칭되지 않은 기존 데이터 삭제" 토글.
- **`ldBuf` / `importWorkRecordsJSON`** 모두 "갱신" 선택 시 미리보기로 진행. 영향 없는 신규-only 케이스는 미리보기 생략.

### 영향 범위
- 엑셀 파일 가져오기 흐름의 UX 변화 (충돌 시 모달 노출).
- 컬럼 자동감지 정밀도 향상 — 기존 파일도 더 정확히 매핑.

## 2. v13.30 — 편집모드 수정 적용 시 항목 중복 생성

### 사용자 보고
> "필터 편집모드 수정 적용 시, 항목 중복 생성됨"

### 원인 분석 (다단계 데이터 흐름 버그)
1. `GET /api/archives/records`(`server/routes/archives.js`)는 매니저/임원에겐 **부서 전체**, 관리자에겐 **테넌트 전체** 레코드 반환 → `aD`에 본인+타인 레코드가 혼재.
2. `POST /api/archives/records/bulk`(`wrBulkPut`)은 **본인 user_id만 DELETE** 후 페이로드 전체를 본인 user_id로 INSERT.
3. 기존 `applyEdits`는 `wrBulkPut(aD)` 호출 → 타인 레코드 원본은 그대로 유지되고 + 매니저 user_id로 사본 INSERT → **중복 발생**.
4. (부수 발견) `PATCH /api/archives/records/batch` 핸들러도 `WHERE user_id=req.user.sub`로 제한되어 매니저가 부원 레코드 편집 시 silent 0-row update.

### 변경 내역

**서버 (`server/routes/archives.js`)**
- `PATCH /records/batch` WHERE 절을 role 기반 스코프로 확장. `member`=본인, `manager`/`executive`=부서, `admin`=테넌트. GET 정책과 일치.
- `DELETE /records/batch`도 동일 정책으로 확장.

**클라이언트 (`업무일지_분석기.html`)**
- `applyEdits` 재작성: `wrBulkPut(aD)` → `wrUpdateRecords` (PATCH /batch)로 변경 행만 부분 업데이트.
- cascade 픽스(같은 수주번호 미편집 행의 ocmt/oclient 고정): 실제 값이 바뀐 행만 `recordsToSave`에 포함하도록 `changed` 플래그 추가.
- 로컬(IndexedDB) 모드는 `wrUpdateRecords`가 정의되지 않으므로 기존 `wrBulkPut(aD)` 폴백 — 단일 사용자 환경이라 안전.
- `ldBuf` / `importWorkRecordsJSON` 모두 `wrBulkPut` 직후 `wrGetAll`로 `aD` 리로드 — 신규 INSERT된 레코드의 신규 id 반영해 후속 편집 PATCH가 stale id로 silent 실패하는 문제 차단.

### 영향 범위
- 매니저/임원/관리자 역할에서 편집 적용이 이전에는 위험한 동작이었음 — 본 수정으로 안전.
- 일반 사용자(member)는 기능적으로 변화 없음. 다만 PATCH 경로로 전환되어 페이로드 크기 감소, 서버 부하 감소.
- import 흐름은 동일한 user_id 스코프 이슈가 잠재적으로 남아 있음(매니저가 부서 전체 데이터를 import → bulk가 모두 본인 user_id로 INSERT). 별도 보고된 적은 없어 후속 작업으로 분류.
